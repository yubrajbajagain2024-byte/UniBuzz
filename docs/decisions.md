# Decisions

Settled choices and why they were made. Do not re-open one without a reason; when one changes, edit
its row and say why and when.

| Decision | Why |
| --- | --- |
| Social network first; Explore tools second | Product identity (README §"Product direction") |
| No custom backend; row-level security is the security model | One less thing to run and get wrong; every rule is testable offline in PGlite |
| All non-UI code in `packages/shared` | Web and mobile share everything except screens |
| npm workspaces + Turborepo, not pnpm | Nothing extra to install; Vercel and Expo support it as is |
| Hand-written `types/database.ts` | Kept deliberately in step with the migrations; regenerating is optional |
| Every new migration ships with a `supabase/rollbacks/*.down.sql` and a PGlite suite in `db:test` | Every change is reversible and tested offline, on the repo's and on production's schema order |
| Photos stored untouched; renditions at read time | Photos are the product: originals up to 25 MB, 12 per listing, Next.js images at quality 85–90 with blurred placeholders |
| No payments in the Marketplace | Meet on campus, like Facebook Marketplace |
| Buzz tables unreadable through the API | Only the `buzz_v2_*` functions decide what leaves the database, so a policy mistake cannot leak anonymity |
| Each day's Buzz prompt has one thread per campus and one on Global, owned by no one; answers are its replies by default, or a buzz of their own titled with the prompt (2026-10-28); an answer posted before migration 53 gets the prompt only where its title is blank (Yubraj's PR #54, 2026-10-28) | Answers read together under the prompt instead of as stray untitled buzzes; no anon owns the prompt; the first answer makes the thread, so a day nobody answers leaves nothing |
| A buzz's category is optional, one per buzz, from a fixed list (`BUZZ_CATEGORIES`) that the database also enforces (2026-10-28) | Stored now so category sections can come later; a fixed list keeps sections meaningful; optional keeps posting quick |
| Moderation engine is server-only | Its rules must never be bundled into the app |
| Businesses can never start a conversation | Students are never cold-messaged |
| "Sponsored" only for a recorded paid promotion; "Verified Partner" only with evidence | The database refuses either label otherwise |
| Anonymous listings keep no poster on the listing row | Identity lives in `anonymous_listing_owners`, readable by the poster alone; revealed per chat with `reveal_listing_identity()` |
| Calls built, then paused behind `CALLS_PAUSED`; since 2026-11-02 hidden for the launch | First (2026-10-25) because no iPhone build could carry them without an Apple Developer Program membership; since 2026-11-02 to hold down operating costs (LiveKit) at the launch, the owner's decision. Nothing of them shows: no Audio call or Video call in any chat's bar, no ring or incoming-call screen, no Join banner, no call screen (a link to one opens Messages), no Calls channel on Android; replaced the "Coming Soon" pill a tap on the buttons used to show. A past call keeps its row in the chat as history only (no call back), as the website already showed it. The code, the database functions, the call records and the `livekit-token` function stay. Migration 66 makes the database refuse new calls too, with a guard on `calls` rather than a revoke on `start_call()`, so the function and its grants stay exactly as they were and the rollback restores the schema exactly. Turning calls on takes both, 66's rollback and `EXPO_PUBLIC_CALLS_ENABLED=1` at build time, and only the owner decides when |
| Campus/Global toggle hidden (`SCOPE_TOGGLE_SHOWN = false`) | Every feed stays on the reader's campus for now; the code is kept |
| Posts is a Home section with no tab (`HIDDEN_HOME_SECTIONS = ["posts"]`) | Orbit blends posts and reels; `/?tab=posts` still works |
| Keep legacy identifiers (`apartment-book`, `apartmentbook`) | Renaming breaks builds, deep links and migration history |
| One shared root `CLAUDE.md` on `main`; status in `docs/`, branch notes in `docs/branches/` (2026-10-27) | A per-branch `CLAUDE.md` conflicted on every merge (PRs #43 and #44); instructions and status now each have one home |
| UniBuzz Business v2 builds on v1 (migrations 49 and 50, 2026-10-27): v1 deals are business posts (the table stays `deals`); v1 paid promotions are ads, and `listing_promotions` is the ledger of ad payments | Every v1 caller, label and stat keeps working; deals were never paid, so making them ads would break "Sponsored only when paid" |
| An admin approves an ad by recording its payment (amount and reference); no payment provider yet | "Sponsored" still always means a recorded payment |
| Business team roles: owners and admins run the team, the profile and ad spend; editors post, draft ads and reply; analysts read the numbers only and are never in inquiry chats | Spending is an owner's or admin's call; the fewest people read students' messages |
| Housing ads (a housing business's, or one promoting a listing) run in Housing only; every one needs an admin's Fair Housing check, with a note when the screen flags its words | The Fair Housing Act (42 U.S.C. 3604(c)); the screen flags, a person decides |
| Ads go to signed-in students only, chosen by campus in a daily rotation that is the same for everyone on that campus. In every feed (For You, Reels, Housing; website and app) the first ad follows the 3rd organic row, then at most one per 9 rows; a feed that has ended with 1 or 2 rows ends with its ad (`ADS_FIRST_AFTER`, `ADS_EVERY`; revised 2026-11-03). An ad whose promoted listing or post is also in the feed keeps its slot, and that organic copy is left out (`interleaveAds`; the owner's choice, 2026-11-04). Each time a feed loads its first page again (a pull-to-refresh, a new filter) it asks for its ads again from the first, keeping the old ones on screen until the new arrive; a screen counts an ad's impression once, refreshes included (`nextAdsRequest`, `receiveAds`, `adsToCount`; the owner's brief, 2026-11-04) | Campus is the only targeting: never demographics or activity; "about one per 8 to 10 posts". The first ad used to wait for the 9th row, but each feed's first page has 8 to 12 rows, so For You and Reels never asked for an ad on their first page and a campus with fewer than 9 posts never showed one: approved, paid ads did not reach students. A student still never sees the same thing twice; skipping the ad instead left its slot empty (a feed asks for only as many ads as it has slots), so on a campus with a page or less of listings a Housing ad for one of them never showed (found on staging, 2026-11-04). The app fetched a feed's ads once per screen, so after a pull-to-refresh a paused or ended campaign stayed and a resumed or new one did not show until the screen was opened again (found on an iPhone, 2026-11-04); the database decides by the clock and the ad's state on every call, so asking again is enough |
| Students' reports about businesses and ads go to the business portal's admin queue, not the staff console's | Business admins act on ads; joining the two queues is later work |
| An approved ad shows the copy of its post or listing taken at approval; a change to that post or listing, or to the business's category, pauses the ad until the UniBuzz team looks again (migration 56) | Students see what was reviewed, and nothing reaches them that the UniBuzz team did not see |
| Every ad's words are screened for Fair Housing, not only housing ads' (migration 56) | A business's category is its own to change, so it cannot decide whether its words are checked |
| A business sees an inquiry chat, and the student in it, only once the student has written (migration 56) | Tapping "Message" is not consent to be known to the business |
| A video's processing details are written by the website's server with the service role, never by a signed-in session (migration 55) | Ads and Reels rely on a video's size and length; only the provider knows them |
| The business portal's sections, in this order: Overview, Inbox, Advertisements, Products & Services, Analytics, Billing; Settings apart at the bottom (2026-10-28; Inbox moved up from third the same day) | The owner's briefs: the sidebar first, then "a dedicated Inbox directly below Overview"; one order everywhere (sidebar and drawer) so people find things by place |
| Stories live 24 hours, carry a post's four audiences, and the server decides who sees one, when it expires and who counts as a viewer (migration 58, 2026-10-30) | The owner's brief: Instagram's stories with privacy enforced in the backend. The rules are migration 44's, so a story and a post mean the same by "campus", "friends" and "selected" |
| A story is shared from the publish screen ("Your story" beside Post), not from a camera mode of its own (2026-10-30) | The camera's row was just fixed as BUZZ, POST, REEL, SNAP; the publish screen already has the editing tools and the audience picker a story needs |

| A Buzz thread is laid out like Reddit's: words across the row, quiet actions at the right, subtle neutral thread lines that fold their branch when tapped, a band between conversations, a button to the next one (2026-10-30) | The owner's Reddit screenshots; one neutral line colour reads calmer than a colour per anon, and the alias mark already says who wrote each reply |
| From a Buzz list, the full-screen viewer goes on through that list's buzzes with media, up and down, then its next pages; the list behind is never changed (2026-10-30) | The owner's brief: Buzz browses like Orbit and Reels. Reading the list's next pages without adding them to it keeps its scroll position and what it shows exactly as left |
| A buzz's photos and video open in the app's full-screen viewer as an anonymous page: the alias and words as on the card, Buzz's own votes, replies and share; never a name, a profile, a post action or a link out of the words (2026-10-30) | The owner's brief: one immersive viewer for Orbit, Reels and Buzz. Buzz v1 opened there too; the v2 port moved it to the chat's photo viewer without a recorded reason.
